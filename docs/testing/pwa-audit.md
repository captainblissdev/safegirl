# PWA audit of `app/interface` (14 October 2026)

An audit of the SafeGirl interface as a progressive web app, followed by
three fixes on `feature/pwa-hardening`. The audit ran against the
production build (`npm run build`, served by `vite preview`) in headless
Chrome, with `ml_service` and the gateway (authentication disabled,
local development only) running locally.

## Summary

| Area | Before | After |
|---|---|---|
| Installable | No: the manifest had no icons | Yes: no installability errors |
| Favicon | 404 on every page load | `favicon.ico` and an SVG favicon |
| Manifest colours | `#6e39c8` (an unused purple) and `#ffffff` | `#f3efe7`, the page background |

## Manifest and icons

**Before.** `name` and `short_name` "SafeGirl", `display: standalone`,
`start_url` and `scope` "/", `theme_color #6e39c8`,
`background_color #ffffff`, `icons: []`. Chrome's installability check
reported `manifest-missing-suitable-icon` and `no-acceptable-icon` (an
icon of at least 144 px is required), and `/favicon.ico` returned 404,
which Lighthouse logged as a console error.

**After.** A heart in a circle, in the app's palette (a `--paper` heart
on `--teal`), generated by `app/interface/scripts/generate-icons.mjs`
(`npm run generate-icons`). The script uses only Node and its built-in
zlib, so no dependency was added.

| File | Size | Use |
|---|---|---|
| `pwa-192x192.png`, `pwa-512x512.png` | 192, 512 | manifest, purpose `any` |
| `maskable-512x512.png` | 512 | manifest, purpose `maskable`; full-bleed teal, heart inside the safe zone |
| `apple-touch-icon.png` | 180 | `<link rel="apple-touch-icon">` |
| `favicon.ico` | 16, 32, 48 | `<link rel="icon">` |
| `safegirl-icon.svg` | vector | `<link rel="icon" type="image/svg+xml">`, and the design source |

**Colours.** The app's tokens (`App.css` and `index.css`): page
background `#f3efe7`, `--ink #183b39`, `--ink-soft #52706b`,
`--teal #176b68`, `--teal-dark #0d4b4a`, `--mint #dceee7`,
`--paper #fffdf8`, `--coral #d96b4e`, `--coral-dark #a94435`,
`--line #c9ddd4`. The app has no coloured top bar, so `theme_color` and
`background_color` are both the page background, `#f3efe7`; the browser
bar and the splash screen then match the page. The
`<meta name="theme-color">` in `index.html` was changed to match.

Chrome's installability check after the change: **no errors**; no
4xx responses and no console errors on load.

## Service worker

`vite-plugin-pwa` 0.20.5 in `generateSW` mode, registered by
`registerSW.js` with `registerType: "autoUpdate"`.

- **Precache:** `index.html`, the JS and CSS bundles, `registerSW.js`,
  the manifest, and (after the fix) the icons and favicons: 11 entries,
  355 KiB.
- **Runtime caching:** none. Nothing outside the precache list is ever
  stored.
- **`/api` is never cached.** There are no runtime routes; `/api/query`
  is a POST, which the Cache API cannot store; and in the test every
  `/api/query` response came from the network. After a chat session,
  Cache Storage held only the precached static files.
- **Navigation fallback.** Every page load is answered with the cached
  `index.html`. Before the fix this included `/api/...` and `/health`
  typed into the address bar (nothing was cached, but the app shell was
  shown instead of the server's response). **After:** both are on
  `navigateFallbackDenylist` and go to the network; other paths still
  get the app shell.

### Update behaviour after a deploy

The service worker calls `skipWaiting()` and `clientsClaim()`, and
`cleanupOutdatedCaches()` removes the old precache.

1. The next visit is served the old shell from the cache, instantly.
2. The browser re-checks `sw.js` on that navigation (bypassing the HTTP
   cache by default), installs the new version and activates it at once.
3. The open tab keeps running the old code; there is no "update
   available" prompt.
4. The next reload gets the new shell.

A user is therefore at most one load behind, and cannot get stuck on a
stale shell permanently. A tab left open, or a user who stays offline,
keeps the old version until a reload while online. The build has one JS
chunk, so deleting the old cache cannot break an open tab.

## Offline behaviour

| Test | Result |
|---|---|
| Shell cached, server stopped, page offline, reload | The app shell loads from the service worker. |
| Typed question while offline | Canned offline answer with the limited-mode notice. No sign-in and no `/api` request is attempted. |
| Typed disclosure while offline | Offline Safety Net referral, with the 999 / 112 / 1195 / 116 message. |
| Browser reports online, but Google and `/api` are unreachable | Firebase sign-in is tried first, fails as a network error, and the offline pipeline answers in limited mode. No error banner. |
| **First visit while offline** | **Chrome's own "no internet" error page.** Nothing is cached yet, so no SafeGirl page and no help numbers are shown. This is an inherent limit of a web app. |

**Timeouts (fix).** Before, `/api/query` had no timeout and sign-in
waited for Firebase's own timeout, so a stalled connection could leave
the user on "Thinking…" for a long time. After:

- `QUERY_TIMEOUT_MS = 20_000`: per attempt, including reading the reply,
  with an `AbortController`;
- `SIGN_IN_TIMEOUT_MS = 10_000`: Firebase sign-in cannot be aborted, so
  it is raced against the timer.

Both fall back to the offline pipeline in limited mode, whose Safety Net
runs first. A query cancelled by "New chat", "End session" or "Start new
session" rejects with `QueryCancelledError` and shows nothing: no answer
and no limited-mode notice. `src/api/timeouts.test.ts` covers both
timeouts (including that nothing happens 1 ms early), the Safety Net on a
timeout, a fast answer being unaffected with no timers left running, and
cancellation during sign-in, during the query and just before the answer
arrives.

## Topic chips through the full stack

Each chip's question is a verbatim "clear" query from
`resources/eval/retrieval_eval_set.csv`, run through `ml_service` and
the gateway with `research/eval/run_eval.js`, which records retrieval
both scoped to the predicted class and unscoped.

| Chip | Expected | Predicted (confidence) | Scoped top-1 | Unscoped top-1 | Live gateway |
|---|---|---|---|---|---|
| Q01 Contraception | KB-C3 | contraception (0.870) | KB-C3 | KB-C3 | KB-C3, scoped |
| Q05 STI | KB-S5 | sti (0.741) | KB-S5 | KB-S5 | KB-S5, scoped |
| Q09 Pregnancy | KB-P6 | pregnancy (0.820) | KB-P6 | KB-P6 | KB-P6, scoped |
| Q11 General | KB-G3 | **sti (0.441)** | **KB-S4** | KB-G3 | KB-G3, unscoped |

**Q11 is a near miss.** "is it normal for my period to be irregular" is
misclassified as STI. Scoped retrieval would return KB-S4 (STI
symptoms). The live answer is correct only because 0.441 is below the
0.5 scoping threshold, so retrieval runs unscoped. A change to the
threshold or to the model could flip it; it should be re-checked after
either. Not changed in this round.
