# SafeGirl — Master Project Plan
Privacy-preserving digital mentorship for adolescent reproductive health
Revised following panel feedback (25/40, "sounds like a CRUD application") and lecturer guidance (Kevin Khakata)

---

## 1. The core idea

The project centers on one genuine, evaluable ML contribution — a fine-tuned intent classifier —
supported by infrastructure (RAG chat, safety net, PWA shell) that gives it a real job to do.
The system is not "a chatbot with AI in it." It is:

> An intent classifier that improves retrieval-grounded answer quality, evaluated against a
> baseline, on an honestly-labeled synthetic dataset.

## 2. System architecture

**1. Anonymous entry** — PWA, session-token based, no phone number, no login, no PII.

**2. Intent classifier (the ML contribution)** — fine-tuned DistilBERT-multilingual, classifies
each query into: contraception / STIs / pregnancy / GBV-related / general.

**3. Retrieval (RAG)** — classifier output narrows search to the relevant slice of a vetted
knowledge base before embedding-similarity retrieval runs. This is the classifier's functional
role — not just a co-located feature.

**4. Answer generation** — LLM (API-based) generates a response grounded only in retrieved
knowledge-base content. Documented as a runtime AI component: provider, model, role,
configuration, limitations, evaluation of outputs.

**5. Safety net** — separate, deliberately simple keyword-based check for distress/GBV/crisis
language, routed to human referral. Not a trained model — kept transparent and conservative.
Design discussed directly with supervisor.

**6. UI safeguard** — visible in-app disclaimer: not a diagnostic tool, does not replace a
qualified professional.

**7. Session end** — nothing persisted that ties back to identity.

## 3. Dataset methodology (per Kevin's guidance — this is the corrected approach)

**What changed:** MOH/WHO/KDHS sources define categories and ground answers — they are
**not** training data themselves (their language doesn't match how real users ask questions).

**Pipeline:**
1. Define intent classes, each mapped to its authoritative source document(s).
2. Write seed questions by hand (10–15 per class) — grounded in sources, phrased naturally.
3. Expand seeds via **controlled LLM-assisted paraphrasing** — document the model, prompts,
   and generation procedure used.
4. **Manually review every generated example** — remove duplicates/near-duplicates, check for
   unsupported medical claims, check for safety and appropriateness.
5. Natural Kenyan phrasing (Sheng, English–Swahili code-switching), if included, must be
   reviewed by someone competent in the language and domain — never generated unreviewed.
6. **Build an independent test set separately** — written/validated by a different adult
   reviewer, using a different process than the training-data generation pipeline. Never test
   on data generated by the same LLM/procedure as training data.
7. **Prevent leakage** — paraphrase siblings of the same seed question stay within a single
   split (train or test), never spread across both.
8. **Label the dataset honestly** as synthetic or partially synthetic in all documentation.
   State clearly that conclusions are bounded to this dataset — not a claim of validation for
   real-world deployment with adolescents.

**Ethics note:** avoiding real minors' conversational data significantly reduces — but does not
eliminate — ethical responsibility. Confirm with supervisor (and university ethics process if
needed) whether adult-reviewer involvement requires formal sign-off.

## 4. Evaluation plan

- Train / validation / independent-test split (e.g. 70/15/15), stratified by category.
- Baseline: keyword-matching classifier, for comparison.
- Metrics: precision, recall, F1-score, confusion matrix — **not accuracy alone**.
- Per-category performance reported, with attention to imbalanced/harder classes
  (e.g. GBV-related).
- Concrete error analysis: real misclassified examples, with reasoning on why they failed.
- Retrieval-precision comparison: classifier-narrowed search vs. full-knowledge-base search —
  the evidence that the classifier improves the RAG system, not just sits beside it.
- Research question answered explicitly: does fine-tuning produce a meaningful improvement
  over the baseline for this classification task?
- Dedicated limitations/bias/privacy/ethics section.

## 5. AI tool documentation (per Kevin's distinction)

- **Runtime component** (LLM API used in the chat): document provider/model, role in
  architecture, configuration, limitations, how outputs are evaluated, relevant citations.
- **Development-time use** (AI used for coding/writing help, e.g. Claude): disclose
  transparently — this is not the project's ML contribution.
- Never let the fluency of the RAG chat's LLM output be conflated with the trained
  classifier's own, independently evaluated performance.

## 8. Non-negotiables — do not drift from these

- Do not train a model from scratch (LSTM or otherwise) — fine-tune a pretrained model.
- Do not generate training and test data with the same LLM/process.
- Do not claim the system is validated for real adolescent deployment — only for this dataset.
- Do not let scope creep back into CRUD territory: no admin dashboards, no session history,
  no features beyond the minimal PWA shell unless time remains after core evaluation work.
- Do not present the RAG chat's fluency as the project's ML achievement — the classifier's
  own evaluation stands alone.
